# ERP 제품 기획 및 UX 규칙

작성일: 2026-07-24  
상태: Pilot 제품 규칙 제안  
적용 범위: 파일 올리기, 문서 검토, 문서 만들기, 승인, 거래, 외부 공유, 업무 완료

## 1. 문서 목적

이 문서는 화면 모양이 아니라 ECOYA ERP가 지켜야 하는 제품 규칙을 정의한다.

- 기능 명세와 화면 설계가 서로 다른 상태 정의를 만들지 않게 한다.
- Approval과 Financial tracking을 사용하지 않는 고객에게도 독립적인 제품 가치를 정의한다.
- Confirm, Approve, Share, Complete의 의미와 전이 조건을 고정한다.
- Pilot에서 검증할 최소 정책과 UX 합격 기준을 명확히 한다.
- 백엔드 API, 권한, 감사 이력, 화면 상태의 공통 기준으로 사용한다.

이 문서의 규칙이 기존 화면 문구나 프로토타입 동작과 충돌하면 충돌 항목을 별도 의사결정으로 기록하고, 암묵적으로 화면 동작을 정본으로 간주하지 않는다.

## 2. 제품 가치 정의

### 2.1 Approval과 Financial tracking을 모두 끈 고객의 가치

독립적인 ERP 가치는 다음 흐름에 있다.

> 흩어진 무역 문서를 검증된 거래 데이터로 확정하고, 외부 공유와 후속 업무 및 변경 이력을 추적한다.

Approval과 Financial tracking은 선택 기능이며 핵심 문서 처리 흐름의 선행 조건이 아니다.

### 2.2 가치가 처음 발생하는 시점

| 단계 | 제품 의미 | 가치 판정 |
| --- | --- | --- |
| 문서 생성·추출 | 검토 가능한 초안을 만든다. | 활성화 가치 |
| 문서 검토·Confirm | 데이터를 재사용 가능한 거래 기준값으로 확정한다. | 최초 지속 가치 |
| 외부 공유 | 확정된 결과를 외부 이해관계자에게 전달한다. | 외부 전달 가치 |
| 업무 추적 | 변경, 누락, 후속 작업을 반복 관리한다. | 반복 사용 가치 |

첫 지속 가치는 `문서 검토 → Confirm`에서 발생한다. 문서 생성 횟수만으로 제품 가치를 판단하지 않는다.

### 2.3 Pilot 이후 과금 가설

사용자가 비용을 지불할 이유는 다음 반복 행동에서 검증한다.

`문서 유입 → 필드 검토 → Confirm → 외부 공유 → 변경·후속 업무 추적`

검증 지표:

- 조직별 주간 완료 사이클 수
- Confirm까지 걸린 시간
- 첫 공유까지 걸린 시간
- 재방문 및 동일 거래 후속 문서 처리율
- 수작업 입력, 누락, 불일치 수정 시간 감소
- 외부 공유 후 변경·철회·재전달 빈도

## 3. 공통 상태 모델

기본 흐름:

`Draft → Confirmed → Approval(선택) → Shareable/Shared → Operationally Complete`

Financial tracking은 이 흐름과 독립된 병렬 상태로 관리한다.

### 3.1 상태별 의미

| 상태·행동 | 제품 규칙 |
| --- | --- |
| Draft | AI 추출값 또는 사용자 입력이 아직 확정되지 않은 상태 |
| Confirm | 검토한 값을 거래와 후속 문서에서 재사용 가능한 기준 데이터로 확정 |
| Approve | 권한자가 확정된 문서 또는 변경 결과의 다음 사용을 허가 |
| Share | 허용된 문서 패키지나 링크를 외부에 노출 |
| Complete | 해당 Deal 유형의 운영 종료 조건을 충족 |

Confirm은 승인이나 외부 공유를 의미하지 않는다. Approve는 외부 수신을 의미하지 않는다. Share는 업무 완료를 의미하지 않는다.

## 4. 문서 유형별 Confirm 최소 필드

Confirm 차단 필드는 거래 식별, 문서 대조, 금액 계산, 규제 판단에 필요한 값으로 제한한다. 선택 필드 누락은 Confirm을 차단하지 않는다.

| 문서 유형 | Confirm 최소 필드 |
| --- | --- |
| 견적서 | 고객, 견적일, 유효기간, 통화, 품목, 수량, 단가 |
| 견적송장 | 판매자, 구매자, 문서번호, 문서일자, 통화, 품목, 수량, 단가, 합계 |
| 판매계약서 | 당사자, 계약번호, 계약일자, 통화, 품목, 수량, 단가, 인코텀즈, 결제조건 |
| 발주서 | 공급자, 구매자, PO 번호, 발주일자, 품목, 수량, 단가, 통화, 납기 |
| 상업송장 | 판매자, 구매자, Invoice 번호, 발행일자, 품목, 수량, 단가, 합계, 통화 |
| 포장명세서 | 당사자 또는 거래 식별값, 품목, 포장 수, 순중량, 총중량, 각 단위 |
| 선적지시서 | 송하인, 수하인, 출발지, 도착지, 선박·항차, ETD·ETA, 화물 정보 |
| 수익자증명서 | 수익자, 은행, 계좌, SWIFT, 참조 문서, 금액, 통화 |
| 납품서 | 발송자, 수령자, 납품일, 납품 장소, 품목, 수량 |
| 원산지증명서 | 수출자, 수입자, 원산지, 품목, 참조번호, 발급일 |
| 거래명세서 | 거래처, 대상 기간, 통화, 청구, 지급, 잔액 |
| 차변표 | 당사자, 문서번호, 문서일자, 원거래 참조, 사유, 금액, 통화 |
| 대변표 | 당사자, 문서번호, 문서일자, 원거래 참조, 사유, 금액, 통화 |

필수값이 없으면 실제 문제 필드에 차단 사유를 표시하고, 상단 요약은 해당 필드로 이동할 수 있어야 한다.

## 5. 변경과 재승인

### 5.1 Material change

다음 변경은 거래의 경제적·법적·운영적 의미를 바꾸므로 material change로 본다.

- 거래 당사자 또는 법적 식별값
- 은행, 계좌, SWIFT 및 지급 대상
- 통화, 품목, 수량, 단가, 합계
- 인코텀즈와 결제조건
- 선적지, 도착지, 주요 선적·납품 기한
- 원산지, 규제, 통관 판단 정보
- 승인 또는 공유된 패키지에 포함되는 권위 문서

### 5.2 재승인이 필요하지 않은 변경

- 의미를 바꾸지 않는 오탈자, 공백, 날짜·금액 표시 형식
- 내부 메모, 태그, 담당자
- 외부에 전달되지 않는 운영 메타데이터
- 로고, 글꼴, 강조색 등 출력 스타일

표시 형식 변경이 원본 값이나 계산 정밀도를 변경하면 비중요 변경으로 보지 않는다.

### 5.3 상태 처리

- Approval 사용 시 material change는 기존 승인을 무효화하고 재승인을 요구한다.
- Approval 미사용 시 material change는 기존 Confirm을 stale 상태로 만들고 재Confirm을 요구한다.
- 비중요 변경은 감사 이력만 남기고 승인 상태를 유지한다.

## 6. Conditional approval Pilot 규칙

Pilot에서는 다음 최소 범위만 지원한다.

- Owner, Admin 또는 지정 Approver만 조건부 승인 가능
- 조건 내용, 해결 담당자, 기한 필수
- 한 승인 요청에서 1회 조건부 승인만 지원
- 중첩 조건, 조건 위임, 다단계 조건 체인은 지원하지 않음
- 조건 미해결 시 Share와 Complete를 기본 차단
- Approver가 외부 공유를 명시적으로 허용한 경우에만 예외 허용
- 조건 또는 material field 변경 시 조건부 승인 무효화
- 생성, 변경, 해결, 무효화 이벤트를 감사 이력으로 저장

상태명은 `conditionally_approved`로 유지하며 `approved`와 동일하게 표시하지 않는다.

## 7. Operational completion

### 7.1 설정 범위

Operational completion 기준은 다음 우선순위로 설정한다.

1. 조직 기본 정책
2. Deal 유형 템플릿
3. 권한자가 사유를 기록한 개별 예외

개인 사용자가 임의로 완료 기준을 바꾸는 기능은 제공하지 않는다.

### 7.2 기본 완료 조건

- Deal 유형별 필수 문서가 Confirm됨
- 필수 운영 업무와 마일스톤이 완료됨
- 차단 위험이 해소되거나 권한자 예외가 기록됨
- 필수 외부 전달이 있는 경우 전달 절차가 완료됨
- Approval을 사용하는 경우 필요한 승인이 완료됨

### 7.3 Financial tracking을 사용하지 않는 Deal

Financial tracking이 꺼진 Deal은 위 운영 조건을 충족하면 `Operationally Complete`로 표시한다.

- 지급 완료, 정산 완료, 수금 완료로 추정하지 않는다.
- `financial_tracking=off` 상태를 보존한다.
- 재무 데이터 부재를 0원 또는 완료로 변환하지 않는다.

## 8. 외부 공유 보장 범위

### 8.1 보장 가능한 상태

| 상태 | 보장 조건 |
| --- | --- |
| 링크 생성 | 서버가 접근 범위, 만료, 토큰을 생성함 |
| 발송 요청 접수 | 서버가 발송 작업을 접수함 |
| 공급자 전달 | 이메일 공급자 webhook으로 전달 결과를 수신함 |
| 열람 | 인증된 링크 접근 또는 viewer 이벤트를 기록함 |
| 수신 확인 | 수신자가 명시적인 확인 행동을 완료함 |

### 8.2 보장하지 않는 사실

- 발송 요청만으로 이메일 전달 완료를 주장하지 않는다.
- 이메일 전달 완료만으로 사람이 읽었다고 주장하지 않는다.
- 링크 접근만으로 수신자가 내용을 이해하거나 동의했다고 주장하지 않는다.
- `수신 확인`은 명시적인 확인 행동이 있을 때만 사용한다.

현재 구현이 `mailto` 또는 클라이언트 위임 방식이면 `발송됨`이 아니라 `이메일 작성 화면으로 전달됨`으로 표시한다.

## 9. 데이터 분류

| 등급 | 예시 | 기본 처리 |
| --- | --- | --- |
| 공개 조직 정보 | 법인명, 국가, 공개 주소, 대표 연락 채널, 공개 로고 | 조직 외부 표시 가능 |
| 조직 내부 정보 | 담당자, 내부 태그, 업무 상태, 내부 메모 | 조직 구성원만 접근 |
| 제한 정보 | 거래처 식별번호, 계약조건, 가격, 거래·선적·정산 데이터, 문서 원문 | Deal·역할 기반 최소 권한 |
| 고민감 정보 | 개인 연락처·서명, 계좌·은행정보, 세금·신분 식별자, GP·마진, Magic Link 토큰, IP·접근 로그 | 강화된 접근 통제와 감사 |

무역 문서는 기본적으로 제한 정보로 분류한다. 계좌, 신분, 인증 토큰이 포함되면 고민감 정보 정책을 적용한다.

## 10. 화면별 주 결정

각 화면은 사용자가 반드시 내려야 하는 주 결정을 하나로 설명할 수 있어야 한다.

| 화면 | 주 결정 |
| --- | --- |
| 파일 올리기 | 어떤 문서를 처리할 것인가 |
| 필드 검토 | 이 값을 Confirm할 것인가 |
| 거래 연결 | 어느 Deal에 귀속할 것인가 |
| 문서 만들기 | 이 초안을 확정할 것인가 |
| 승인 | 허용, 조건부 허용, 반려 중 무엇인가 |
| 외부 공유 | 누구에게 어떤 패키지를 공유할 것인가 |
| 거래 상세 | 지금 처리해야 할 다음 업무는 무엇인가 |
| 완료 처리 | 운영 종료 조건이 충족되었는가 |

보조 액션은 주 결정을 지원해야 하며 동일한 시각적 위계로 경쟁하지 않는다.

## 11. SNAP 노출 규칙

ERP와 SNAP을 연결하지 않은 고객의 필수 온보딩에서는 SNAP을 노출하지 않는다.

- 첫 ERP 가치 경험을 방해하거나 설정을 차단하지 않는다.
- SNAP이 필요한 맥락에서 선택적 통합으로 제안한다.
- 통합 설정 또는 고급 기능 영역에서 발견 가능하게 한다.
- 연결되지 않은 상태를 오류나 미완료로 취급하지 않는다.

## 12. UX 규칙

### 12.1 첫 가치 도달

- 신규 실무자는 별도 설명 없이 10분 안에 첫 외부 공유를 완료할 수 있어야 한다.
- 테스트 경로는 문서 유입, 필드 검토, Confirm, 공유 대상 선택, 링크 생성 또는 발송 요청을 포함한다.
- 중간 단계에서 제품 내부 용어를 알아야만 진행할 수 있어서는 안 된다.

### 12.2 CTA

- 한 시점에 주 CTA는 하나만 둔다.
- 다음 단계가 바뀌면 주 CTA도 현재 상태에 맞게 교체한다.
- 비활성 버튼에는 이유와 해결 방법을 버튼 인접 영역 또는 tooltip에 제공한다.
- 해결 가능한 문제라면 해당 필드나 화면으로 이동하는 액션을 제공한다.

### 12.3 색상

| 용도 | 색상 의미 |
| --- | --- |
| 파랑 | 선택, 현재 위치, 주 행동 |
| 회색 | 중립 정보, 비활성 |
| 주황 | 확인 권장, 기한 임박, 비차단 경고 |
| 빨강 | 진행 차단, 오류, 위험 |
| 초록 | 완료, 정상, 검증 완료 |

Hover는 중립 배경 변화로 표현하고 상태색과 혼동시키지 않는다. 선택색과 오류색을 동일하게 사용하지 않는다.

### 12.4 AI confidence

AI confidence는 숫자보다 필요한 행동으로 표현한다.

- 바로 사용 가능
- 확인 권장
- 반드시 확인

정확한 confidence 수치는 진단이나 상세 근거에서 보조 정보로만 제공한다.

### 12.5 위험 우선 검토

- 차단 오류와 확인 권장 필드를 먼저 표시한다.
- 정상 필드는 기본 접기 또는 요약이 가능하다.
- 전체 보기와 검색을 항상 제공한다.
- 정상 필드를 숨겨 사용자가 전체 데이터 존재 여부를 오해하게 만들지 않는다.

### 12.6 오류 위치

- 오류는 실제 문제 필드에 표시한다.
- 상단 오류 요약은 보조 수단이며 선택하면 문제 필드로 이동해야 한다.
- 저장 또는 다음 단계 실패 메시지만 상단에 남겨두지 않는다.

### 12.7 반응형·긴 콘텐츠

- 390dp, 768dp, 낮은 세로 해상도, 긴 번역, 긴 거래처명에서 주 CTA가 보여야 한다.
- 3단 화면은 작은 화면에서 단계 전환, 탭 또는 sheet로 변환한다.
- 중요한 저장·Confirm·공유 액션은 긴 필드 목록 아래로 사라지지 않게 한다.
- 긴 파일명과 거래처명은 말줄임과 전체값 tooltip을 함께 제공한다.

### 12.8 빈 상태

빈 상태는 다음 원인을 구분한다.

- 아직 시작하지 않음
- 검색 결과 없음
- 권한 없음
- 처리 실패
- 연동되지 않음

각 빈 상태에는 가능한 다음 행동을 제공하며, 실패처럼 보이는 장식만 표시하지 않는다.

### 12.9 상태 일관성

- Home, 알림, 목록, 상세는 동일한 서버 상태를 사용한다.
- 화면별로 상태 문자열을 독립 생성하지 않는다.
- 파생 상태는 공통 함수 또는 백엔드 계약으로 계산한다.
- 같은 업무를 화면마다 다른 완료·대기 상태로 표시하지 않는다.

### 12.10 외부 Viewer

외부 사용자는 ECOYA 계정 없이 필요한 문서를 확인할 수 있어야 한다.

- 만료 가능한 범위 제한 링크
- 링크 철회
- 검색 엔진 노출 방지
- 공유 패키지 외 데이터 접근 차단
- 열람 감사 이력
- 고민감 문서는 선택적으로 OTP 또는 추가 인증 적용

## 13. Pilot 합격 기준

- 신규 실무자 5명 중 4명 이상이 설명 없이 10분 내 첫 공유 완료
- Happy Path 각 상태에서 주 CTA가 1개 이하
- 모든 비활성 주 CTA에 차단 이유와 해결 행동 존재
- Confirm 차단 오류가 실제 문제 필드와 연결됨
- 정상·주의·차단·완료·선택 상태가 색상만으로도 서로 충돌하지 않음
- 390dp, 768dp, 데스크톱에서 핵심 흐름 완료 가능
- 외부 Viewer가 계정 없이 허용된 문서만 열람 가능
- Confirm, Approve, Share, Complete를 사용자 인터뷰에서 구분 가능
- Approval과 Financial tracking을 끈 조직도 Confirm, Share, Complete 흐름을 완료 가능

## 14. 추가 결정 필요

다음 항목은 Pilot 시작 전 제품·법무·운영 책임자가 확정해야 한다.

- 문서 유형별 필수 필드의 국가·거래 유형별 예외
- 조건부 승인 상태에서 외부 공유를 허용할 기본 정책
- Deal 유형별 Operational completion 템플릿
- 이메일 공급자 webhook을 포함한 발송 상태 보장 범위
- 고민감 문서에 OTP를 강제할 조건
- Material change 판정을 백엔드 필드 목록으로 관리할지 정책 엔진으로 관리할지 여부

## 16. ECOYA 공통 제품 검토 기준

새 기능, donor 기능, 기존 화면, 정책 변경을 검토할 때는 구현 유지 여부보다 사용자의 실제 업무 감소를 먼저 판단한다. 검토자는 중소 수출입 기업의 무역 실무자, 관리자, 구매 결정자 관점에서 반대 증거를 적극적으로 찾는 `adversarial product manager` 역할을 맡는다.

### 16.1 필수 검토 질문

모든 Flow 또는 Spec은 다음 질문에 답해야 한다.

1. 사용자가 이 단계를 수행해야 하는 실제 이유가 있는가?
2. ECOYA가 문서, 거래, 조직 설정 또는 이전 행동으로 자동 판단할 수 있는 사실을 사람이 다시 입력하고 있지 않은가?
3. Approval, Deal, Financial tracking, SNAP이 선택 기능인데도 기본 흐름을 막고 있지 않은가?
4. 동일한 사실을 여러 화면에서 반복 확인하거나 확정하게 하지 않는가?
5. 이 기능이 실제 업무를 줄이는가, 아니면 ECOYA를 관리하는 새 업무를 추가하는가?
6. 실패하거나 이탈해도 입력값과 진행 상태를 보존하고 재개할 수 있는가?
7. 현재 시점에 필요한 다음 행동이 하나로 명확한가?
8. 이 기능이 없어도 핵심 가치가 성립하는가?

질문에 답할 근거가 없으면 추정으로 기능을 유지하지 않고 `Defer until evidence` 또는 `DECISION_REQUIRED`로 기록한다.

### 16.2 단계 분류

각 단계에는 아래 중 정확히 하나의 분류를 부여한다.

| 분류 | 판정 기준 |
| --- | --- |
| Must exist in P0 Happy Path | 없으면 사용자가 최초 지속 가치인 Confirm 또는 필요한 외부 공유까지 도달할 수 없음 |
| Exception-only | 오류, 불일치, 권한 예외, 규제 예외 등 특정 조건에서만 필요하며 정상 흐름에는 노출하지 않음 |
| Optional capability | 특정 조직 설정이나 업무 방식에서 가치가 있지만 기본 흐름의 선행 조건은 아님 |
| Defer until evidence | 문제와 사용 빈도 또는 지불 의사가 검증되지 않아 Pilot 기본 범위에 넣지 않음 |
| Remove candidate | 사용자 결정을 만들지 않고 반복 확인, 중복 입력 또는 제품 관리 업무만 추가함 |

donor 또는 원본 코드에 기능이 존재한다는 사실은 유지 근거가 아니다. 제거하거나 선택 기능으로 내릴 때는 API, 감사 이력, 규제 의무에 미치는 영향만 별도로 확인한다.

### 16.3 필수 결과 형식

제품 검토 결과는 아래 순서로 작성한다.

```md
# [Flow 또는 Spec 이름] 제품 검토

## 사용자와 완료 기준
- 주 사용자:
- 사용자가 해결하려는 실제 업무:
- 이 화면에서 내려야 하는 하나의 결정:
- 완료로 인정할 관찰 가능한 결과:

## Before
1. 현재 단계
2. 현재 단계
3. 현재 단계

## 단계별 판정
| 단계 | 실제 필요 이유 | 자동화 가능 사실 | 중복·기본 흐름 차단 | 실패 후 재개 | 다음 행동 | 분류 | 결정 |
| --- | --- | --- | --- | --- | --- | --- | --- |

## After
1. 줄인 단계
2. 줄인 단계
3. 완료

## 기본 흐름에서 제외
- Exception-only:
- Optional capability:
- Defer until evidence:
- Remove candidate:

## 검증 필요
- 확인할 사용자 행동:
- 필요한 로그 또는 인터뷰:
- 성공·중단 기준:
```

`Before`와 `After`는 화면 수가 아니라 사용자가 내려야 하는 결정과 행동 수로 비교한다. 단계를 다른 화면이나 모달로 옮긴 것은 흐름 단축으로 계산하지 않는다.

### 16.4 P0 Happy Path 게이트

P0 Happy Path에 남는 단계는 모두 다음 조건을 충족해야 한다.

- 사용자가 지금 내려야 하는 결정이 하나 있음
- 시스템이 자동으로 알 수 없는 입력 또는 명시적 동의가 필요함
- Approval, Financial tracking, SNAP 같은 선택 기능을 사용하지 않아도 진행 가능함
- 실패 시 입력값을 잃지 않고 같은 지점에서 재개 가능함
- 주 CTA가 하나이며 비활성일 때 이유와 해결 행동이 인접해 있음
- 완료 후 사용자가 얻은 결과가 화면 상태나 감사 이벤트로 확인 가능함

하나라도 충족하지 못하면 기본 흐름 유지 사유를 별도로 입증하거나 다른 분류로 내린다.

### 16.5 검토 경계

- 기존 구현을 유지해야 한다고 가정하지 않는다.
- 기능 수를 성과로 보지 않는다.
- 기술적으로 어렵다는 이유만으로 사용자 문제를 축소하지 않는다.
- donor 기능이 있다는 이유만으로 계승하지 않는다.
- 예외 처리 능력을 Happy Path 단계 수 증가로 해결하지 않는다.
- 화면을 추가하는 대신 자동화, 기본값, 점진적 공개, 인라인 복구를 먼저 검토한다.
