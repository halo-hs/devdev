# 원본 코드 기반 ERP 기능·정책 SSOT 전면 최신화 Goal

제품 상태, Confirm, 승인, 공유, 완료 및 공통 UX 판단은
`docs/product-planning-ux-rules.md`를 함께 기준으로 사용한다.

## 1. 목표

원본 코드베이스를 직접 분석하여 현재 기획서, 기능 명세, 정책 문서와의 불일치를 찾아낸다.

단순히 기존 문서를 교정하는 작업이 아니다. 실제 코드에 구현된 메뉴, 화면, 상태, 권한, API 계약과 정책 요구사항을 기준으로 다음을 수행한다.

1. 원본 코드의 전체 기능을 다시 인벤토리화한다.
2. 코드와 기존 SSOT·기획서의 정합성을 비교한다.
3. 누락되거나 오래된 문서를 최신화한다.
4. 구현에는 존재하지만 문서에 없는 기능을 복원한다.
5. 문서에는 있지만 구현되지 않은 기능을 식별한다.
6. 개인정보, 멤버, 구독, 결제, 문서 보관 정책의 누락 여부를 점검한다.
7. 백엔드 API를 연결할 수 있을 정도로 화면 상태와 데이터 계약을 구체화한다.
8. 불명확한 사항은 임의 확정하지 않고 의사결정 항목으로 남긴다.

코드는 현재 동작의 증거지만 항상 올바른 기획 의도는 아니다.

1. 사용자가 최근 명시한 제품 결정
2. 승인된 최신 SSOT 및 정책 문서
3. 현재 원본 코드의 실제 동작
4. 프로토타입에서 검증된 개선 흐름
5. 과거 기획서 및 레거시 문서

코드와 문서가 다르면 코드를 그대로 정답으로 간주하지 않는다. 차이를 분류하고 어떤 쪽을 수정해야 하는지 판단한다.

## 4. 불일치 판정

- `MATCH`: 코드와 문서가 일치함
- `DOC_STALE`: 코드에 구현되어 있으나 문서가 오래되었거나 누락됨
- `CODE_GAP`: 문서에 요구사항이 있으나 구현이 없거나 부족함
- `DECISION_REQUIRED`: 코드와 문서가 다르며 제품 결정이 필요함
- `POLICY_EXISTS`: 정책이 명시되어 있고 구현과 일치함
- `POLICY_STALE`: 정책 문서가 현재 기능이나 운영 방식보다 오래됨
- `POLICY_REQUIRED`: 필요한 정책 자체가 정의되어 있지 않음
- `LEGAL_REVIEW_REQUIRED`: 국가, 계약, 서비스의 법적 지위에 따라 법무 검토가 필요함
- `IMPLEMENTATION_GAP`: 정책은 있으나 UI, API 또는 백엔드 구현이 부족함

## 22. 금지사항

- 원본 코드를 읽지 않고 화면만 보고 추정하지 않는다.
- 기능 존재 여부와 제품 유지 여부를 혼동하지 않는다. 제품 유지 판단은 `docs/product-planning-ux-rules.md`의 공통 제품 검토 기준과 단계 분류를 적용한다.
- 코드에 없다는 이유로 정책 항목을 삭제하지 않는다.
- 문서에 있다는 이유로 구현 완료라고 판단하지 않는다.
- 보관기간, 환불 조건, 법적 의무를 임의 확정하지 않는다.
- 개인정보 데이터를 샘플 문서에 그대로 노출하지 않는다.
- 레거시 문서를 확인 없이 삭제하지 않는다.
- 사용자 요청 없이 Notion을 직접 수정하지 않는다.
- 이 작업에서는 제품 코드를 수정하지 않는다.
- 모든 문서 작업이 완료되기 전에 커밋·푸시하지 않는다.

## 23. 완료 조건

- 원본 코드의 모든 메뉴와 경로가 인벤토리에 포함됨
- 역할별 접근 차이가 문서화됨
- 주요 액션과 상태 전이가 문서화됨
- 입력 필드와 표시 전용 값이 구분됨
- 반복 품목 구조가 문서화됨
- API 계약과 화면 상태가 연결됨
- 개인정보 데이터 지도가 완성됨
- 멤버 정책이 정의되거나 결정 필요로 등록됨
- 구독·결제 정책이 정의되거나 결정 필요로 등록됨
- 문서 유형별 보관표가 작성됨
- 취소·중단·삭제 거래의 추적 정책이 포함됨
- 코드와 문서의 모든 차이에 판정값이 있음
- 미결 정책마다 결정권자와 목표 결정일이 있음
- 문서 링크와 참조 경로가 유효함
- 레거시 문서가 최신 SSOT를 덮어쓰지 않음
- 마지막 검증 날짜와 Git commit SHA가 기록됨
