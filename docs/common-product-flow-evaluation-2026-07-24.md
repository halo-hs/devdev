## 2. 전체 판정

**기능 범위와 API 경계는 충분하지만 P0 Happy Path가 과도하게 넓다.**

현재 구조는 문서 유입, AI 추출, 필드 검토, Deal 연결, 승인, 외부 공유, 선적, 정산, 운영 감시까지 하나의 연속된 제품처럼 보인다. 실제로는 다음 두 층으로 분리해야 한다.

1. **독립 ERP 핵심 가치**
   - 문서를 받거나 만든다.
   - AI가 사실을 구조화한다.
   - 사용자는 위험·누락만 확인한다.
   - Confirm으로 재사용 가능한 업무 데이터가 된다.
   - 필요한 문서를 외부에 안전하게 공유한다.
2. **선택형 운영 확장**
   - Deal 연결과 후속 업무 추적
   - 승인 정책
   - 선적, 정산, 운영 감시
   - 결산 리포트, 영업 성과
   - SNAP과 외부 연동

두 번째 층이 첫 번째 층을 막으면 안 된다. 현재 프로토타입은 화면 기능은 풍부하지만 이 경계가 일부 흐려져 있다.

## 3. 첫 가치와 P0 정의

### 첫 가치

첫 지속 가치 발생점은 **문서 검토 후 Confirm**이다. 이때 문서 속 사실이 검색·재사용·공유 가능한 조직 데이터가 된다.

Pilot 활성화 완료점은 **첫 Confirm 문서를 외부에 안전하게 공유**한 시점으로 본다.

### P0 Happy Path

1. PDF 업로드, 기존 문서 선택 또는 문서 생성
2. AI 자동 분류·추출·초안 작성
3. 누락·불일치·낮은 신뢰도·필수값만 우선 검토
4. Confirm
5. `공유하기`, `추천 Deal에 연결`, `완료` 중 하나 선택

Deal, 승인, 재무 추적, SNAP은 조직 정책이나 사용 목적에 따라 4번 또는 5번 이후에 붙는다.

## 4. 단계별 분류

### Must exist in P0 Happy Path

- 다중 파일 업로드와 업로드 결과 보존
- 문서 유형 자동 판별
- 문서 유형별 최소 Confirm 필드 검증
- AI 추출값과 원문 근거 대조
- 위험·누락 필드 우선 검토
- 입력값 자동저장, 이탈 후 재개
- Confirm과 Confirm 결과의 명확한 상태
- 확정 문서의 PDF 생성·다운로드
- 외부 공유용 문서 선택, 보안 링크 생성, 철회
- 링크 생성·열람처럼 시스템이 실제로 관측한 전달 이력
- 모든 실패 상태에서 입력값 보존과 같은 위치의 재시도

### Exception-only

- AI 문서 유형 판별 실패 시 수동 선택
- OCR 실패·부분 실패·중복 문서 처리
- 필수 Trigger 누락과 비표준 문서 안내
- 출처 간 값 충돌과 5-Way Match 불일치
- material change 후 재확인·재승인
- 은행 계좌 변경, 수량·금액 불일치 등 고위험 예외
- 링크 만료·철회·접근 제한
- 동시 편집 충돌과 오래된 탭 복구
- Deal 후보 없음, 중복 Deal, 연결 실패

### Optional capability

- Confirm 이후 Deal 연결 또는 신규 Deal 생성
- 조직 정책에 따른 승인·반려
- 이메일 수신 첨부 자동등록
- 앱 내 이메일 발송
- 문서 템플릿, 로고, 강조색, 출력 스타일
- AI 문구 다듬기와 AI에게 묻기
- 선적, 정산, 운영 감시
- 결산 리포트, 영업 성과
- SNAP 증거와 외부 서비스 연동
- 거래처 별칭 학습과 일괄 등록

### Defer until evidence

- 복잡한 다단계 conditional approval
- AI 건강도 점수와 경영 요약을 주요 의사결정 근거로 사용하는 기능
- 실제 수신 확인 없이 발송 완료를 보장하는 기능
- 사용 증거가 없는 세밀한 개인화 대시보드
- 모든 역할에 동일하게 노출되는 고급 재무·성과 분석

### Remove candidate

- 같은 사실을 업로드, 문서 상세, Deal 상세에서 반복 Confirm하는 흐름
- Confirm 전에 강제되는 Deal 연결
- 모든 고객에게 강제되는 승인·재무·SNAP 단계
- 정상 필드까지 전부 펼쳐 놓는 기본 화면
- 필드별 저장 버튼과 전체 저장의 중복
- 각 필드 아래 반복되는 추천값·AI 설명 라벨
- 메뉴 이동만 수행하는 과도한 빠른 실행 카드
- 동일한 전달값과 고객 전달 제어의 중복
- 실제 전송을 관측하지 못하면서 `전달 완료`로 표현하는 상태
- 목록에서도 충분한 업무를 무조건 상세 패널로 다시 여는 구조

## 6. 현재 흐름의 주요 문제

### 6.1 Confirm의 의미가 약해짐

필드 검토, Deal 연결, 승인, 문서 확정이 서로 가까이 배치되어 사용자가 무엇이 데이터 확정이고 무엇이 조직 통제인지 구분하기 어렵다.

**수정 원칙:** Confirm은 데이터 사실 확정, Approve는 조직 승인, Share는 외부 공개, Complete는 운영 종료로 분리한다.

### 6.2 자동화가 검토 업무를 충분히 줄이지 못함

AI가 이미 읽은 정상 필드와 추천 근거가 모두 펼쳐지면 사용자는 추출 결과 전체를 다시 읽어야 한다.

**수정 원칙:** 기본 화면은 차단 필드, 불일치, 낮은 신뢰도, material change만 노출한다. 정상 필드는 `전체 보기`에서 확인한다.

### 6.3 동일 사실의 소유권이 분산됨

문서의 추출값, 생성 문서의 필드, Deal의 기준값이 각각 수정 가능한 형태로 보이면 어느 값이 정본인지 모호해진다.

**수정 원칙:** 문서는 출처값, Deal은 운영 기준값을 가진다. 출처값 변경은 Deal 기준값을 자동 덮지 않고 변경 제안으로 들어온다.

### 6.4 선택 모듈이 기본 제품처럼 보임

승인, 재무, SNAP, Pro 리포트가 제품의 필수 진행 단계처럼 보이면 독립적인 문서 ERP 가치가 약해진다.

**수정 원칙:** 기능은 유지하되 조직 설정과 entitlement에 따라 필요한 사용자에게만 노출한다.

### 6.5 상태 보장의 범위가 과장될 위험

Magic Link 생성은 관측 가능하지만 외부 메일 클라이언트의 실제 수신은 별도 전송 제공자나 webhook 없이 보장할 수 없다.

**수정 원칙:** `링크 생성`, `발송 요청`, `열람`, `수신 확인`을 별도 상태로 관리하고 관측한 사실만 표시한다.

## 7. Before / After

### 현재 프로토타입 판정

현재 구현은 Before 그대로가 아니라 **Before와 목표 After 사이**에 있다.

이미 개선된 부분:

- 문서 만들기에서 승인은 선택 사항이며 승인 없이도 문서 확정이 가능하다.
- 문서 확정 전에는 고객 전달이 노출되지 않고, 확정 후 주요 CTA가 고객 전달로 바뀐다.
- 확정 후 문서 만들기·전달·Deal 후속 작업이 분리되어 있다.
- 업로드와 문서 만들기에 자동저장·수동 저장 상태가 존재한다.
- 문서 유형 판별 실패, OCR 실패, 필수값 누락 등 예외 상태가 작업 위치에 표시된다.
- Deal 상세는 문서별 출처와 거래 기준값을 구분하는 방향으로 구성되어 있다.

아직 남은 차이:

- 파일 올리기의 필수 필드 안내와 주요 CTA가 `Confirm`이 아니라 `거래 연결`을 목표로 한다.
- 파일 올리기에서 Deal 연결이 문서 검토의 다음 필수 단계처럼 보인다.
- 정상 필드도 기본 목록에서 모두 렌더링되고 필드마다 상태·출처·신뢰도·설명이 반복된다.
- 문서 만들기 상단에서 저장, PDF, 승인 요청, 문서 확정이 동시에 보여 주요 결정이 경쟁한다.
- 문서 정돈의 품목·문구·로고·스타일 기능이 선택형 꾸미기보다 필수 단계처럼 인식될 여지가 있다.
- Home, 거래, 선적, 정산 등 후속 모듈이 첫 문서 가치와 시각적으로 같은 우선순위에 놓인다.

따라서 아래 Before는 **현재 화면을 그대로 묘사한 목록이 아니라**, 원소스의 모든 기능을 한 경로에서 수행할 경우 발생하는 최대 흐름이다. 현재 프로토타입의 실질적인 남은 핵심 단계는 다음과 같다.

1. 문서 업로드 또는 생성
2. 유형·필수값·위험 검토
3. 파일 올리기는 Deal 연결, 문서 만들기는 문서 확정
4. 선택적으로 승인 또는 고객 전달
5. Deal·선적·정산 후속 작업

가장 먼저 고칠 불일치는 파일 올리기의 3번을 `문서 Confirm`으로 통일하고, Deal 연결을 Confirm 이후 선택 행동으로 이동하는 것이다.

### Before

1. 문서 업로드 또는 생성
2. 문서 유형과 추출 요약 확인
3. 정상 필드를 포함한 전체 필드 검토
4. 추천값과 AI 설명 확인
5. 필드 저장
6. Deal 후보 확인 또는 신규 Deal 생성
7. Deal 연결
8. 문서 정돈·품목·로고·스타일 설정
9. 승인 요청·승인
10. 문서 확정
11. Magic Link 생성
12. 이메일 또는 링크 전달
13. 선적·정산·완료 상태 추적

### After

1. 문서를 올리거나 만든다.
2. ECOYA가 자동 분류·추출하고 차단 항목만 제시한다.
3. 사용자가 예외를 수정하고 Confirm한다.
4. `공유하기`, `추천 Deal 연결`, `여기서 완료` 중 다음 행동 하나를 선택한다.
5. 선택한 운영 모듈만 후속 상태를 이어받는다.

Happy Path의 사용자 결정은 최대 네 번으로 제한한다.

## 8. 우선 수정 순서

### P0

1. Confirm을 Deal·승인·재무에서 분리
2. 위험 필드 우선 보기와 정상 필드 접기

## 9. 최종 결론

ECOYA의 문제는 기능 부족보다 **기능 경계가 Happy Path 안에서 경쟁하는 것**에 가깝다. 원소스 기능과 API 계약은 버리지 않고 유지하되, 기본 제품은 다음 한 문장으로 설명되어야 한다.

> ECOYA는 무역 문서를 받아 사실을 구조화하고, 사람이 위험만 확인해 확정한 뒤 필요한 상대에게 안전하게 전달하도록 한다.

Deal·승인·선적·정산·성과 분석은 이 확정 데이터를 이어 쓰는 선택형 운영 기능이다. 이 순서를 지키면 기능을 삭제하지 않고도 사용자의 ECOYA 관리 업무를 크게 줄일 수 있다.
