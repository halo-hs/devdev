4. 업무 규칙과 표시 기준

  • 알림을 열거나 사용자가 읽음 처리하면 서버에 즉시 저장하고 같은 계정의 다른 기기에 동기화한다.
  • 읽음·수신·원천 업무 완료는 서로 다른 사건이며 읽음 처리로 업무를 완료하지 않는다.
  • 실시간 연결이 끊기면 마지막 동기화 시각을 표시하고 재연결 또는 주기 조회를 사용한다.
  • 보존기간은 LR-003 법무 검토가 소유하며 기간 미확정은 읽음 동기화와 업무 상태 구현을 차단하지 않는다.

근거: OD-007.

갱신 계약

SSE는 구현 선택지이며 제품 계약은 합의된 갱신 목표시간이다. 주기 조회 대체 경로, 재연결, 오프라인 상태를 포함한다. 현재 60초 주기 조회가 업무 목표시간에 충분한지는 결정이 필요하다.

꼭 지켜야 할 점

  • 읽음은 행동 항목 완료를 호출하지 않는다.
  • 업무 건수와 읽지 않은 알림 수를 같은 숫자로 설명하지 않는다.
  • 여러 기기의 읽음 상태는 서버에 저장된 같은 기록으로 맞춘다.
  • 알림 조회 실패를 빈 상태로 표시하지 않는다.
  • 보관/삭제/접근 불가 대상은 안전한 복구를 제공한다.
  • 알림 AI 문맥은 worker의 조건부 보조 처리다. 설정이 없거나 모델 호출이 실패해도 규칙 기반 사건 평가와 알림 흐름 자체를 AI 실패로 중단하지 않는다.

다음 방식은 알림 상태의 기준으로 사용하지 않는다.

  • 브라우저 저장값만을 여러 기기의 읽음 기준으로 사용하는 방식
  • 알림 열기를 연결 업무의 해결·완료로 처리하는 방식
  • 읽지 않은 알림 수를 남은 업무 수와 같은 값으로 사용하는 방식

화면 문구

  • “새 알림”과 “미완료 작업”을 구분한다.
  • 배지는 접근 가능한 설명을 가진다.
  • 실패 시 재시도와 내 할 일 직접 진입을 제공한다.

5. 현행 QA 점검 항목

이 절은 앞선 제품 계약을 검증하기 위한 점검 항목이며, 독립적인 제품 요구사항을 추가하지 않는다.

실제 통과 기준은 6~7장의 현행 구현 상태와 프론트·API·백엔드 원본 근거가 확인된 범위로 제한한다.

  • 알림을 연 뒤 실제 업무는 진행 중으로 남는다.
  • 실제 업무 완료 후 내 할 일 상태가 갱신된다.
  • 두 기기에서 읽음이 동기화된다.
  • 오프라인/재연결/주기 조회 대체 경로가 중복·누락을 만들지 않는다.
  • 권한이 사라진 대상은 정보 노출 없이 복구한다.
  • 알림 조회 실패를 빈 목록으로 오인하지 않는다.
  • AI 문맥 설정이 없는 환경에서도 규칙 기반 알림이 생성·조회된다.

6. 정책 및 구현 상태

구현 상태

플랫폼은 행동 항목 완료와 알림 열기를 코드상 분리하지만 읽음을 브라우저 저장소에 보관하고 약 60초마다 조회한다. IMPLEMENTATION_GAP이다.

알림 AI 문맥은 사용자가 직접 호출하는 별도 API가 아니라 intelligence worker 내부의 조건부 경로다. 현재 이 호출은 공통 llm_call_logs에 연결되지 않는다.

서버는 권한 범위의 업무 이벤트 목록/스트림과 알림 설정을 제공하지만, 알림의 “읽음”을 여러 기기에 동기화하는 표준 서버 수신 기록은 확인되지 않았다. 따라서 “읽지 않음/새 알림” 건수는 아직 지속 가능한 API 계약이 아니다. 주기 조회/SSE는 구현 방식이며 갱신 목표시간, 커서/재연결, 보존 기간은 승인이 필요하다.

알림 첫 조회, 백그라운드 재연결/갱신, 원천 업무 변경은 각각 별도 처리 상태다. 읽지 않음, 빈 목록, 오프라인/업데이트 지연, 403 대상, 삭제된 대상, 스트림 실패를 구분한다. 알림 열기는 행동 항목 완료 API를 호출하지 않는다.

현재 판정: 읽음/업무 분리는 개념과 행동 항목 구현에서 MATCH다. OD-007에 따라 서버 읽음 저장·기기 동기화·연결 실패 표시를 구현해야 하므로 IMPLEMENTATION_GAP이다. 보존기간은 LR-003의 출시 전 법무 관문이며 현재 개발·내부 QA를 차단하지 않는다(TR-013).
