FS-02 — 확정 및 승인

결정 근거: TRADE-DOC-001 — QA 절의 규범 경계 · TRADE:DEC-TRD-009 — 지원 locale과 fallback · TRADE:DEC-TRD-010 — 접근성 기준과 검증 범위

읽는 순서: 목적·범위 → 화면 항목·행동·이동 → 단계별 정상·오류·복구 → 업무 규칙·표시 기준 → QA → 정책·구현 상태 → 개발 참조

2026-07-31 결정 반영 — 아래는 확정 정책이다. 구현·QA 상태는 이 문서가 관리하지 않는다.

  • DEC-TRD-003 — Pilot 기본 Approval mode는 **disabled**다. 선택한 조직에만 optional을 제공하고 required·conditional은 고객 통제 요구 확인 후 확장한다. 승인 의미가 바뀐 revision은 재승인한다.

1. 문서 목적과 적용 범위

사용자 문제와 완료 결과

검토 담당자의 사실 확인과 권한자의 승인이 같은 행동처럼 보이면 책임과 부수 효과를 예측할 수 없다. Pilot 완료는 현재 문서 버전을 Confirm하고 변경 전후값·수정자·작업 오너·사유·시각·근거를 Job history에 기록한 상태다. 향후 Approval 모드가 활성화된 경우에만 같은 문서 버전의 승인 조건을 추가한다.

사용자와 권한

  • owner/admin/member: 본인 담당 또는 공동 작업자로 내부 공유된 문서의 수정·Confirm
  • Pilot disabled: 모든 역할에 승인 요청·승인·승인 대기 UI 기본 비노출
  • Approval 모드 활성 시: owner/admin/member는 승인 요청, 지정 승인자는 승인/반려

표준 의미

  • 확정: 검토한 사실을 업무 데이터로 채택
  • Job history: 변경 전후값·수정자·작업 오너·사유·시각·근거 기록
  • 승인 요청·승인·반려·재승인 필요: Approval 모드가 활성화된 경우에만 사용하는 Backend 보존 상태와 UI 의미

2. 화면 항목·버튼·이동

화면/구역 화면에 보이는 항목 버튼/행동 처리 결과 이동/유지 화면
문서 머리말 문서명, 문서 종류, 현재 문서 버전, 문서 상태 문서 새로고침 최신 문서 버전과 권한 반영 현재 문서 유지
초안 편집 문서 필드, 품목, 첨부, 품질 경고 저장 새 문서 버전 저장 편집 화면 유지
Job history 변경 전후값, 수정자, 작업 오너, 사유, 시각, 근거 이력 보기 현재 문서 버전의 변경 근거 확인 현재 문서 유지

3. 단계별 정상·오류·복구 흐름

단계별 통합 상태표

화면 섹션 상태 구분 진입 상태 사용자 행동 API·외부 호출 처리 중 상태 성공 상태 실패 및 복구 다음 흐름
문서 머리말 화면 표시 문서 조회 중 현재 문서 버전 열기 문서 조회 API 문서 조회 중 문서 버전·상태 표시 권한 없음, 문서 없음, 서버 오류를 구분; 재시도 또는 목록 복귀 초안 편집
초안 편집 저장 상태 초안 필드/첨부 수정 저장 API 저장 요청 중 새 문서 버전이 “초안” 유지 검증, 오래된 버전, 권한 오류; 미저장 입력 유지, 충돌 시 재조회 확정
Pilot 확정 실행 저장 상태 필수값 검토 완료 현재 문서 버전 Confirm 확정 API 확정 요청 중 “확정됨”과 Job history 기록 필수값, 오래된 버전, 저장·이력 오류; 이전 상태와 입력 유지 FS-03 또는 FS-04
승인 요청 — 활성 모드 저장 상태 초안, 승인 필요 승인 요청 승인 요청 API 승인 요청 중 “승인 대기” 및 승인 이벤트 생성 승인자 없음, 오래된 버전, 금지; 초안 유지 승인함
승인함 — 활성 모드 저장 상태 + 화면 표시 승인 대기 승인 또는 반려(사유) 목록 조회·승인/반려 API 결정 요청 중 “승인됨” 또는 “반려됨” 오래된 문서 버전, 권한 없음, 처리 기록 저장 실패; 서버 상태 유지 후 재조회 확정 또는 초안 편집
중요 변경 — 활성 모드 저장 상태 승인됨 중요 필드 수정 저장 API 저장 및 기존 승인 무효화 중 “재승인 필요” 승인 상태 초기화·이력 저장 실패; 수정값 유지 후 최신 상태 재조회 승인 요청

API·외부 호출은 이 행동에서 실제 연결이 발생하는지를 보여준다. 정확한 메서드·경로·응답은 7장 개발 참조의 같은 행동에서 확인한다.

4. 업무 규칙과 표시 기준

중요 변경과 Job history

기본 검토 후보:

  • 금액, 통화
  • 판매자/구매자/거래처
  • 문서 종류
  • 필수 품목/수량/단가
  • 결제 조건/지급기한
  • Deal 연결 또는 거래 방향

Pilot 기본 Approval은 disabled다. 조직이 향후 required 모드를 활성화한 경우에만 Owner가 설정 > 업무 정책 > 승인에서 문서 종류와 금액 기준을 정한다. 제품 전체에 단일 금액 기준을 강제하지 않는다. 근거: OD-001.

Pilot에서는 위 변경을 권한으로 일률 차단하지 않고 Job history에 남긴다. Approval 모드가 활성화된 경우 위 중요 변경과 승인 대기 중 수정은 새 리비전의 재승인 필요로 전환한다. 이전 승인은 현재 리비전에 재사용하지 않으며 확정·공유를 차단하고 승인 요청 CTA를 표시한다.

Member는 본인 담당 또는 공동 작업 문서·Deal의 일상 필드를 수정할 수 있다. 중요 변경에는 변경 전후값·수정자·작업 오너·사유·시각·근거를 남긴다. 조직·과금·영구 삭제·권한 설정은 이 범위에 포함하지 않는다.

Approval 모드가 활성화된 경우 다음 방식은 재승인으로 인정하지 않는다.

  • 중요 수정 뒤 승인 상태를 단순히 “없음”으로 숨기고 확정을 계속 허용하는 방식
  • 확정하기를 재승인 대신 사용하는 방식
  • 문구·메모처럼 거래 의미가 바뀌지 않는 모든 수정에 무조건 재승인을 요구하는 방식

공통 UI 품질 계약 적용

공통 UI 품질 계약의 지원 locale 전체에서 Confirm은 현재 문서 버전의 사실 확정, Approval은 활성화된 승인 모드의 승인·반려라는 서로 다른 업무 의미를 유지한다. 버튼명·상태·오류·복구 안내가 두 행동을 합치거나 번역에 따라 바꾸어서는 안 된다. Confirm과 활성 Approval의 주요 행동은 키보드로 도달·실행·취소할 수 있고, 화면 읽기 도구가 이름·역할·현재 상태와 오류를 구분해 읽을 수 있어야 한다.

근거: DEC-TRD-009, DEC-TRD-010.

5. 정책·구현 QA 점검 항목

이 절은 앞선 제품 계약을 검증하기 위한 점검 항목이며, 독립적인 제품 요구사항을 추가하지 않는다.

실제 통과 기준은 6~7장의 현행 구현 상태와 프론트·API·백엔드 원본 근거가 확인된 범위로 제한한다.

  • Pilot에서 승인 요청·승인·승인 대기 UI가 기본 노출되지 않는다.
  • owner/admin/member가 접근 가능한 문서를 수정→Confirm하고 Job history를 확인한다.
  • Confirm한 문서 버전과 Job history의 변경 전후값·수정자·작업 오너·사유·시각·근거가 일치한다.
  • Backend 승인 API와 상태 계약은 삭제되지 않는다.
  • Approval 모드가 활성화된 경우에만 승인 요청·승인·반려·재승인 UI와 차단 조건이 적용된다.
  • 지원 locale 전체에서 Confirm과 활성 Approval의 의미·상태·오류를 구분하고, 키보드와 화면 읽기 도구로 각 행동을 도달·실행·취소하고 결과를 확인할 수 있다.

6. 정책 및 구현 상태

현재 충돌

현재 Frontend의 승인 요청·승인·승인 대기 UI는 Pilot 기본 비노출 정책과 충돌한다. Backend 승인 기능과 상태 계약은 보존 대상이다. 승인 상태 초기화 뒤 확정을 허용하는 현재 동작은 향후 Approval 활성 모드에서 상태 우회가 되므로 별도 CODE_GAP으로 유지한다.

7. 개발 참조

기획자가 읽는 Pilot 정상 결과와 실패·복구는 3장의 같은 행동 행에 통합했다. 아래 승인 상세값은 삭제 대상이 아닌 보존된 Backend 계약이며, Pilot Frontend 기본 UI를 의미하지 않는다.

  • 반려됨: 사유와 수정→재요청 동선

화면 기능별 API 연결

화면 기능 API 요청 화면 성공값 개발 참조 응답/실패
문서 열기 GET /trade/generated-documents/:id 문서 ID 초안/승인 대기/승인됨/확정됨, 현재 리비전 DocumentView; 403/404
초안 저장 PATCH /trade/generated-documents/:id {content} “저장됨”, 새 리비전 DocumentView; 검증/충돌
승인 요청 POST .../:id/submit 빈 본문 “승인 대기” approval_status=pending
승인 POST .../:id/approve 빈 본문 “승인됨” approval_status=approved; 403/충돌
반려 POST .../:id/reject {reason} “반려됨”, 반려 사유 approval_status=rejected
확정 POST .../:id/confirm 선택 quality_acknowledged “확정됨” status=confirmed; 승인/재승인 필요 오류
승인 이력 GET .../:id/approval-events 문서 ID 처리자·행동·시각 이력 ApprovalEventsResponse

변경 요청은 인증된 사용자와 문서 ID를 사용하며, 반려에는 사유가 필요하다. 응답은 결과 문서 상태와 리비전을 반환하고, 승인 이벤트 목록은 처리자·행동·시각을 제공한다. Docgen, Confirm 권한 검사는 서버가 수행하며 버튼을 숨기는 것만으로 권한을 대신하지 않는다.

문서 최초 조회, 초안 저장, 승인 요청, 승인 결정, 확정은 각각 별도 처리 중/오류 상태를 가진다. 404, 403, 오래된 버전/충돌, 검증, 승인 필요/재승인 필요, 일시 오류를 구분한다. 변경 실패 시 마지막 서버 상태를 그대로 표시하고 화면 흐름을 앞당기지 않는다.

현재 판정: Backend 승인 API와 감사 이벤트는 보존한다. Pilot Frontend 승인 UI 비노출과 Job history 필수값은 IMPLEMENTATION_GAP, 활성 Approval 모드의 중요 필드 정의는 OPEN-016, 승인 초기화 우회는 CODE_GAP(TR-004)이다.
